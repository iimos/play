# super_index: опорные цены бумаг берутся не на тот момент

**Статус: сделано (24.10.2026).** Исправлено в `cmd/indexsuper/indexsuper.go`
(`refCutoff`, `sessionModes`) и `store/superindex.go`
(`IndexIntradaySession`, `EveningSessionInWindow`); история пересобрана за
40 дней, сверка с фактом — в разделе «Итог» ниже. Дефект «плоских» дней
(см. «Попутно найдено») остаётся открытым.

Найдено при проверке пропусков за последние 40 дней (18.10.2026). Пропуски
закрыты, но попутно выяснилось, что синтез `super_index` завышает дни после
вечернего движения предыдущего дня: расхождение с фактическим закрытием индекса
достигает **3.5 %**.

## Что происходит

В `cmd/indexsuper/indexsuper.go`, `buildIndexDay`:

```go
anchor, ok, err := storage.IndexDailyClose(ctx, indexID, prevDate)   // закрытие дня
...
cutoff := atHour(prevDate, fallbackEndHour)                          // 19:00
prevCloses, err := closes.get(ctx, storage, prevDate, cutoff)        // цены бумаг до 19:00
```

Дальше уровень индекса считается как

```
level = anchor * (1 + Σ wᵢ · (pᵢ / refᵢ − 1))
```

Здесь `anchor` — **закрытие дневной свечи** индекса (`interval = 24`). У MOEX
дневная свеча закрывается вместе с вечерней сессией (последняя сделка ~23:50),
то есть `anchor` включает вечернее движение. А `refᵢ` — цены бумаг на **19:00**
предыдущего дня, до вечерней сессии.

Итог: якорь уже стоит на уровне 23:50, а прибавки `pᵢ/refᵢ − 1` отсчитываются
от цен 19:00 — вечернее движение предыдущего дня учитывается дважды. Ошибка
равна взвешенной доходности бумаг за вечернюю сессию:

```
ошибка ≈ Σ wᵢ · (close_23:50ᵢ / price_19:00ᵢ − 1)
```

Тот же дефект у валютной части: `fxPrev` берётся `FXMainClose(prevDate, cutoff)`
по тому же 19:00, а `fxLast` идёт из `FXCloseSeries(sessStart, windowEnd)`, где
`windowEnd` — конец сессии (23:50). Поэтому RTS*/IMOEXCNY/RUBMI завышаются ещё и
на вечернем движении курса.

Затронуты не только «дни после вечернего движения», но и выходные: субботняя и
воскресная сессии строятся от того же пятничного якоря.

## Почему это не «просто пересобрать»

Пересборка с текущим кодом даёт то же самое: опорные цены по-прежнему берутся на
19:00. Нужен фикс в коде, иначе дни 10–12.10 и 17.10 останутся завышенными.

## Предлагаемый фикс

> Раздел оставлен как исходный замысел. Что в итоге сделано — в «Итоге» ниже:
> одной полночи недостаточно, потому что не все индексы торгуются вечером.

Момент, на который берутся опорные цены, должен совпадать с моментом якоря —
с закрытием дневной свечи (23:50), а не с концом основной сессии:

```go
// cutoff — момент, на который берутся опорные цены бумаг и курса.
// Должен совпадать с моментом, к которому относится anchor: IndexDailyClose
// отдаёт закрытие дневной свечи, а она включает вечернюю сессию (до 23:50).
// Раньше здесь был atHour(prevDate, fallbackEndHour) (19:00), и вечернее
// движение предыдущего дня попадало в синтез дважды (см. plans/super-index-ref-time.md).
cutoff := dayMSK(prevDate).AddDate(0, 0, 1)
```

`closes.get` в SQL дату не использует — она нужна только как ключ кэша, а запрос
идёт окном `[cutoff − staleDays, cutoff)` с `argMax(pr_close, time)` по каждой
бумаге. То есть `cutoff = 00:00 следующего дня` означает «последняя ненулевая
цена за предыдущий день, иначе за предыдущие 30 дней». `FXMainClose` фильтрует
`toDate(time) = prevDate AND time < cutoff`, поэтому 00:00 следующего дня её тоже
не ломает — бар в 00:00 в `super_eq`/`super_fx` не попадёт.

Заодно стоит проверить семантику `staleDays`: сейчас окно поиска цены — 30 дней
назад от cutoff, а не от `prevDate`, при сдвиге cutoff на день это тот же
30-дневный запас, ничего не меняется.

`fallbackEndHour` (19) остаётся нужен только для окна торгов, когда интрадей
индекса недоступен (история глубже `intradayDays = 60`). Для таких дней
`validate` начнёт ругаться на несовпадение последнего бара 19:00 с дневным
закрытием 23:50 — это артефакт валидации, а не ошибка синтеза: строки внутри
дня остаются согласованными, просто окно короче. Либо ослабить `validate` для
дней без интрадея, либо оставить как есть и знать про это.

## Проверка после фикса

1. Пересобрать затронутые дни (список выше), проверить сходимость:

```sql
select s.indexid, s.d, s.last_close, c.day_close,
       round((s.last_close - c.day_close) / c.day_close * 100, 2) diff_pct
from (select indexid, toDate(time) d, argMax(pr_close, time) last_close
      from tr.super_index
      where toDate(time) >= today() - 40 and indexid in ('IMOEX', 'RTSI', 'MOEXBMI')
      group by indexid, d) s
join (select indexid, toDate(time) d, argMax(close, time) day_close
      from tr.index_candles
      where toDate(time) >= today() - 40 and indexid in ('IMOEX', 'RTSI', 'MOEXBMI')
      group by indexid, d) c using (indexid, d)
order by abs(diff_pct) desc
```

Ожидание: рублёвые индексы — доли процента (остаточное расхождение из-за
разницы моментов последней сделки бумаги и индекса), RTSI — до ~0.2–0.3 %.
Для сравнения, до фикса на обычных днях расхождение IMOEX было 0.03–0.2 %.

2. Пересобрать историю за 40 дней целиком:

```bash
go run main.go build-index-super --start 2026-09-08 --force
```

Дни с расхождением > 0.5 % можно и точечно:

```bash
go run main.go build-index-super --start 2026-10-10 --end 2026-10-12 --force
go run main.go build-index-super --start 2026-10-17 --end 2026-10-17 --force
go run main.go build-index-super --start 2026-10-06 --end 2026-10-06 --force
```

3. Прогнать `validate`-предупреждения по логу сборки: их не должно быть для
   рублёвых индексов на днях с интрадеем.

## Итог: что сделано (24.10.2026)

Одной полночи оказалось мало: не все индексы торгуются вечером. У MOEX10,
MXSHAR и большинства тематических/отраслевых индексов дневная свеча
закрывается вместе с основной сессией (~19:04), поэтому сдвиг cutoff на 00:00
следующего дня ломал уже их — те же ~3 %, но в другую сторону. Момент опорных
цен теперь определяется по индексу.

Код:

- `refCutoff` (`cmd/indexsuper/indexsuper.go`) — момент опорных цен:
  - интрадей индекса за референсный день: конец последней 10-минутной свечи.
    Если закрытие этой свечи расходится с дневной свечой больше порога
    `validationThresholdPct` (усечённый/битый интрадей) — предупреждение и
    переход на режим сессии;
  - интрадея за день нет (`intradayDays = 60`): режим сессии по свечам за 60
    дней до этой даты — вечерний индекс получает 00:00 следующего дня,
    основной 19:00. Окно ограничено датой, поэтому ответ не зависит от того,
    что загрузилось позже (частичный текущий день, выходные);
  - `sessionModes` — кэш режима на прогон сборки (`Build`/`Builder`), иначе на
    историю глубже интрадея уходил бы запрос на каждый индекс каждый день.
- `closesCache`: `cutoff` добавлен в ключ кэша. Раньше ключом была только дата,
  и индексы с разным моментом закрытия делили один набор опорных цен — это
  само по себе давало 3 % у MOEX10/MXSHAR после первого варианта фикса.
- `IndexIntradaySession` отдаёт ещё и `close` последней свечи; убран повторный
  запрос за предыдущий день в ветке `isToday` (`refCutoff` возвращает `prevEnd`).
- `store/superindex.go`: `EveningSessionInWindow` — есть ли у индекса вечерние
  свечи в окне `[d − 60 дней, d)`. Сознательно не `max(end)` по всей истории:
  такой ответ зависел от времени суток запуска и не выражал смену режима по
  дате (вечерняя сессия у индексов появилась с 28.09.2026).
- Валютная часть (`FXMainClose(prevDate, cutoff)`) на текущих данных — no-op:
  в `super_fx` вечерних котировок нет (`USD000UTSTOM` заканчивается ~19:00),
  поэтому разрыв источника у RTS* фиксом не лечится (см. ниже).

Проверка после пересборки 40 дней (`build-index-super --start 2026-09-08
--force`):

| индекс | max расхождение | среднее | дней > 0.5 % |
|---|---|---|---|
| IMOEX | 0.14 % | 0.023 % | 0 |
| MOEXBMI | 0.15 % | 0.022 % | 0 |
| RTS*/RUBMI | 1.03–1.09 % | ~0.35 % | 9–11 из 37 |

Дни из таблицы выше: 10.10 −0.04 %, 11.10 +0.02 %, 12.10 +0.01 %, 17.10
−0.05 % (IMOEX; остальные индексы в тех же пределах). «Плоских» дней за 40
дней не осталось. Предупреждения `validate` остались только у RTS*/RUBMI
(разрыв валютного источника) и по одному у MREF/MOEX10 на границе порога.

История глубже интрадея проверена отдельно (июль 2026, дневное закрытие
19:04, вечерней сессии у индексов ещё нет): IMOEX/MOEX10 сходятся в пределах
0.33 %, ложного «вечернего» режима нет.

Осталось открытым (вне этого фикса):

- **«плоские» дни** (см. ниже) — автоматической защиты по-прежнему нет,
  лечатся только `--force`;
- **валютная часть**: вечерних котировок USD/RUB в `super_fx` нет, поэтому
  RTS* остаются с систематическими ~0.4 % (в доке допуск ≤1.1 %);
- пересборка обязательна на любом стенде: `buildDay` пропускает дни с готовыми
  строками (`CountSuperIndexForDate > 0`), старые завышенные значения сами не
  перезапишутся.

## Попутно найдено: «плоские» дни в super_index

**Статус: не исправлено** — остаётся открытым пунктом, к этому фиксу не
относится.

15.10 у 30 индексов и 16.10 у 17 индексов весь день `pr_close` — одно и то же
значение (`min = max`). Причина: день собирался, когда `super_eq` за него был
пуст (гонка с перезагрузкой дня / ранний триггер), `buildIndexDay` получил
`lastBarTime.IsZero()`, но не вышел, а построил строки от форвард-филла одних
референсных цен.

Дальше день уже не исправлялся сам: `buildDay` пропускает индекс/день, если
`CountSuperIndexForDate > 0`, то есть «плохие» строки навсегда считаются
готовыми. Принудительная пересборка (`--force`) их лечит — 15–16.10 пересобраны,
`min != max` на всех индексах.

Что стоит сделать отдельно (не в рамках этого фикса):

- не вставлять строки за прошедший день, если ни одной строки бумаг не нашлось
  (сейчас `lastBarTime.IsZero()` проверяется только для сегодняшнего дня);
- либо после вставки проверять, что день не «плоский» (например, `pr_high >
  pr_low` хотя бы у части баров), и не считать его готовым.

## Контекст: что было с пропусками

За 40 дней пропусков по дням в основных таблицах не осталось. Отсутствующие дни
у `super_fx`, `bond_daily`, `iss_openpositions`, `index_weights` — выходные
(источник по ним пуст, `super_index` для них собирается из данных бумаг, которых
в выходные тоже нет). Пропуски `index_candles`/`super_index` 19–20.09 и 26–27.09
— тоже выходные: ISS отдаёт по ним неполный набор индексов (например, только
`IMOEX2`), это проверено запросами к ISS, а не недогрузка.

По инструментам внутри дней есть единичные дыры (например, `CNY000000TOD` в
`super_fx` 25.09–07.10), но они не связаны с исправленной багой дневной
перезагрузки и требуют отдельного разбора.
